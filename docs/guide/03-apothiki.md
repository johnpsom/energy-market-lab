# Κεφάλαιο 3: Η αποθήκη δεδομένων

## Το πρόβλημα
Αν κάθε φορά που εκπαιδεύεις το μοντέλο τραβάς ξανά τα δεδομένα από τα API, το σύστημα
είναι αργό, εξαρτάται από το δίκτυο και δεν είναι αναπαραγώγιμο. Αν πάλι τα αποθηκεύεις
χωρίς σχέδιο, τα ίδια δεδομένα διπλογράφονται και το ιστορικό μπερδεύεται. Χρειάζεσαι μια
αποθήκη με λίγους κανόνες.

## Βασικές αποφάσεις

### Long format
Μία γραμμή ανά (χρόνος, διάσταση, τιμή), π.χ. ανά τεχνολογία παραγωγής:

```
ts                  zone  fuel          source  value
2025-06-01 12:00    GR    Solar         entsoe  3400
2025-06-01 12:00    GR    Wind Onshore  entsoe   900
```

Αν εμφανιστεί νέα τεχνολογία, το σχήμα δεν αλλάζει. Στο wide format θα χρειαζόταν νέα στήλη.

### Σύνθετο primary key
Το κλειδί αποτελείται από όλες τις στήλες που ορίζουν μοναδικά μία τιμή: χρόνος, ζώνη,
διάσταση και πηγή. Η πηγή μπαίνει στο κλειδί, ώστε δύο πηγές που δίνουν την ίδια ποσότητα
(π.χ. πρόβλεψη και παρατήρηση παραγωγής) να συνυπάρχουν χωρίς να αλληλοεπικαλύπτονται.

### Upsert και idempotency
Μια λειτουργία είναι **idempotent** όταν το να την τρέξεις δέκα φορές δίνει το ίδιο
αποτέλεσμα με το να την τρέξεις μία. Το πετυχαίνεις με upsert: εισαγωγή και, αν υπάρχει
ήδη το κλειδί, ενημέρωση της τιμής.

```python
from sqlalchemy.dialects.sqlite import insert

stmt = insert(table).values(batch)
stmt = stmt.on_conflict_do_update(
    index_elements=primary_key_columns,
    set_={c: stmt.excluded[c] for c in value_columns},
)
conn.execute(stmt)
```

Έτσι μπορείς να ξανατρέξεις ένα script μετά από σφάλμα ή να επικαλύψεις ημερομηνίες χωρίς
να χαλάσεις τα δεδομένα. Προσοχή στα όρια: η SQLite περιορίζει τις μεταβλητές ανά
εντολή, άρα γράφεις σε κομμάτια (chunks).

## Οι πίνακες που χρειάζεσαι

| Πίνακας | Περιεχόμενο |
|---|---|
| prices | Τιμές ανά ώρα, ζώνη, προϊόν (day-ahead κ.λπ.) |
| load | Ζήτηση (πρόβλεψη και πραγματική) |
| generation | Παραγωγή ανά τεχνολογία (πρόβλεψη και πραγματική) |
| weather | Καιρός ανά τοποθεσία και μεταβλητή |
| fuel | Ημερήσιες τιμές καυσίμων και CO₂ |
| forecasts | Οι προβλέψεις του ίδιου του μοντέλου |

## Ώρα στην αποθήκη
Διάλεξε μία σύμβαση και τήρησέ την παντού: ή αποθηκεύεις σε UTC και μετατρέπεις στην
απεικόνιση, ή αποθηκεύεις τοπική ώρα χωρίς ζώνη και τη διαχειρίζεσαι προσεκτικά στην αλλαγή
ώρας. Η σύγχυση εδώ δημιουργεί σφάλματα μίας ώρας που περνούν απαρατήρητα.

## Το «vintage»: πότε έγινε γνωστή κάθε τιμή
Για έναν ειλικρινή έλεγχο (Κεφ. 6) χρειάζεται να ξέρεις **τι ήταν γνωστό τότε**. Αν η
αποθήκη αντικαθιστά πάντα την παλιά πρόβλεψη με την τελευταία, χάνεις το ιστορικό
προβλέψεων. Δύο λύσεις:

- Χωριστή πηγή για προβλέψεις (`source = 'weather_forecast'`, όχι ίδια με την παρατήρηση).
- Στήλη `issued_at` (πότε εκδόθηκε η πρόβλεψη), που μπαίνει και στο κλειδί.

Όποιο δεδομένο θα ήθελες αργότερα να ξαναδείς «όπως ήταν εκείνη τη στιγμή» πρέπει να
αποθηκεύεται έτσι.

## Επέκταση: από SQLite σε PostgreSQL/TimescaleDB
Ξεκίνα με SQLite, που δεν χρειάζεται διακομιστή. Γράψε το σχήμα με τρόπο συμβατό με
PostgreSQL, ώστε η μετάβαση να είναι αλλαγή ενός connection string. Σε PostgreSQL με
TimescaleDB οι πίνακες χρονοσειρών γίνονται hypertables για γρήγορα ερωτήματα σε μεγάλο
όγκο.

## Συχνά λάθη
- Αποθήκευση τιμών στο κλειδί χωρίς την πηγή, με αποτέλεσμα σύγκρουση πρόβλεψης και
  παρατήρησης.
- Διαγραφή και επανεγγραφή ολόκληρου πίνακα αντί για upsert.
- Αποθήκευση κωδικών και tokens στον κώδικα. Χρησιμοποίησε αρχείο περιβάλλοντος εκτός
  version control.

## Άσκηση
Φτιάξε έναν πίνακα με σύνθετο κλειδί, γράψε το ίδιο ημερήσιο αρχείο τρεις φορές με upsert
και επιβεβαίωσε ότι ο αριθμός γραμμών δεν αλλάζει. Μετά άλλαξε μία τιμή και ξαναγράψε.

## Πρόσθετη ανάγνωση
